Design system Graph language
Direction B · Lavender · values from design/tokens.css

1 · Dependency-graph nodes

Shape, colour and label together, never colour alone. Rules are a dot and a label; rule sets and flows are tinted containers.
NFR-31 · FR-50

2 · Edges, drawn by how certain the link is

A misleading graph is worse than a partial one: resolved links are solid, late-bound links are dashed, broken links are marked.
FR-21 · FR-50
Contains Rule set to member rule. 1-px hairline, no arrowhead.
Runs · resolved bean-ref or instance, fixed at startup. 1.5-px solid, arrowhead.
Runs · dynamic lookup Looked up by name or class when the flow runs. Dashed; labelled on hover.
Runs · unresolved Nothing is registered under that name. Dashed error colour into a missing node.
Highlighted path Hover or selection path: the same style in ink, 2 px; its ends gain a stronger border.
All edges are orthogonal, with 8-px rounded corners, and routed by ELK so they never cross a node.

3 · Flowchart steps

One node per command, its kind named in the overline; run steps are tinted by what they run. Async work gets its own lane and joins back at its await.
FR-53

4 · Together: nightlyRepriceFlow

The same dynamic lookup and missing target, encoded the same way in the flowchart and in the dependency graph.
FR-50 · FR-53
Dynamic-lookup steps get a dashed border in their target's type colour; a step whose target is missing turns error-coloured, with the same dot the problems list uses.
